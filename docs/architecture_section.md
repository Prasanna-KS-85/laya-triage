**How to read the diagram.** Colour tells you where something runs: blue is the local Mac, orange is Kaggle's GPUs, yellow is the Hugging Face Hub, grey is the GitHub repository, green is a GitHub-hosted Actions runner, purple is an external source, and red marks a frozen contract or a gate. Band A is *build time*: how a model is made, once per model version. Band B is *run time*: what happens on every new issue. Band C is *how it was built*: the process that keeps the numbers honest.

### The idea in one paragraph

Maintainers lose time deciding whether a new issue is a bug, a feature request or a question. LLM-based bots are slow, cost money, return text that has to be parsed and cannot say how sure they are. Laya Triage replaces them with a small, fast **decision model**: it reads the issue, answers one multiple-choice question in a single forward pass, and returns a calibrated probability for each option. The GitHub Action then acts only when the model is confident enough for that label, and otherwise marks the issue for a human. It runs on a free CPU runner, calls no paid API, and never generates text.

### Band A: build time (once per model version)

1. **Data preparation (local).** The official NLBSE train and test files are fetched from a pinned upstream commit and verified by a cryptographic hash. Rows whose content also appears in test are dropped from training, a stratified validation split is carved out, and every row gets a synthetic ID and a content hash so leakage can be checked mechanically. One shared function, `preprocess()`, cleans the text (HTML comments, long logs, links) and is used identically in training, evaluation and at run time. The raw data is never committed because the upstream license is unspecified.
2. **Fine-tuning (Kaggle).** The cleaned rows go to a private Kaggle dataset (never the test split). A notebook pins every library version, tokenises the rows with the exact packing the runtime will use (a hash proves that the Kaggle and local tokenisation are identical), fine-tunes the base Laya checkpoint on two GPUs with Laya's RLCD recipe, fits a first temperature, and pushes the weights to the Hugging Face model repository.
3. **Model registry (Hugging Face).** The base checkpoint is public and pinned by revision. Our fine-tune is stored as one revision, and a second revision, which differs only in the temperature in its config file, is the one the Action ships. The repository is public, so runners download it without a token.
4. **Calibrate, gate, evaluate (local).** On the CPU, with the same numerics as the runner, the model is scored on validation. The temperature is refit on validation, per-label thresholds are chosen with a bootstrap lower bound on precision, and everything is committed and tagged *before* the test split is touched. The pre-declared test evaluation is then run exactly once, against four reference points: a majority-class floor, TF-IDF with logistic regression, the base Laya checkpoint without fine-tuning, and the published NLBSE results.
5. **Release (GitHub).** The thresholds and the pinned model revision live in one default config. The package, the composite Action, a Linux dependency lock generated by CI, the generated README and model card, and the specification are tagged and released; consumers pin the full commit SHA.

### Band B: run time (every new issue)

A trigger starts the consumer's workflow. The composite Action checks the runner, restores a cached Python environment and a cached model snapshot (or builds and downloads them on a cold start), then runs `python -m laya_triage`:

- **event_loader** reads the event from the file the runner provides, never from a shell command, and skips pull requests, bot authors and issues that are already labelled or escalated.
- **preprocess()** turns the title and body into the same state the model was trained on.
- **Classifier** loads the pinned Laya revision on the CPU and returns one probability per label in a single forward pass.
- **policy** compares the probability of the predicted label with that label's threshold. Above it: apply the label. Below it, or for a label whose threshold is "never": escalate to a human with the needs-human label and, if enabled, a short fixed-text comment.
- **github_client** performs the writes with retries (nothing at all in dry-run mode, the default), and **reporter** writes a job-summary table and a JSONL log that contains no issue text.

Issue-triggered runs can read the caches but cannot write them, so a scheduled or manual warm-up run keeps them fresh.

### Key concepts

- **Laya, a decision model.** A non-autoregressive encoder that never writes text. It takes a *state* (here the issue) and typed *questions*, and returns probabilities, so there is nothing to parse and nothing to hallucinate.
- **The typed question.** One *choice* question with the options bug, feature and question. The wording and the option order are packed into the input, so changing them changes the model; they are frozen.
- **Sequence packing.** The question, each option (marked by a mask token) and the issue are laid out in one sequence, so every token can see all the others. Options are inputs, not a fixed output layer.
- **Encoder and decision head.** A bidirectional ModernBERT-large encoder reads the sequence. A small two-layer head reads the encoder's hidden state at each option's mask position and produces one score per option.
- **RLCD fine-tuning.** Reinforcement learning with proper scoring rules: the reward is highest only when the reported probabilities match the truth, which discourages over-confidence. It is combined with a soft cross-entropy term.
- **Temperature scaling and calibration.** Dividing the scores by one fitted number changes the confidence but never the predicted label. The shipped temperature was refit on validation because the first fit, on a small calibration slice, over-softened the probabilities. Calibration is measured by expected calibration error.
- **answer_confidence.** The probability of the predicted label, and the quantity the thresholds are compared with. Laya's other confidence field only describes the shape of the distribution and is not used for gating.
- **Per-label thresholds.** For each label, the lowest cut-off whose bootstrap lower bound on validation precision reaches the target. If no cut-off qualifies, the label is never applied automatically.
- **Coverage and precision.** Coverage is the share of issues the Action labels by itself; precision is how often those labels are right. Raising a threshold trades coverage for precision.
- **Escalation and dry-run.** Whatever the model is not sure about goes to a human. Dry-run, the default, changes nothing and only reports what it would do.
- **Fail-soft.** Runtime problems (a model download, a rate limit) are logged and the run still succeeds, so the Action never blocks someone's pipeline; misconfiguration fails loudly.
- **Pinned revisions and frozen contracts.** The model, the dependencies and every third-party action are pinned by revision or commit. The question, the cleaning function, the data splits, the thresholds and the model revision change only through a specification edit, a changelog entry and a fresh evaluation.
- **Spec-driven, pre-registered evaluation.** The project follows a written specification phase by phase, and the test evaluation was pre-declared and run once, after the protocol and thresholds were committed. Later exploratory analyses reused its predictions and are labelled post-hoc.

### Where things live

| Path | What it holds |
|---|---|
| `PROJECT_SPEC.md` | the single source of truth: requirements, decisions, gates, changelog |
| `src/laya_triage/` | the run-time package |
| `action.yml`, `constraints-linux.txt` | the composite Action and its pinned dependency lock |
| `config/triage.default.yml` | model revision, thresholds, labels, defaults |
| `training/` | dataset build, shared item packing, the Kaggle notebook |
| `eval/` | baselines, evaluation, gating, plots |
| `results/` | every metric file, figure and run record the README is generated from |
| `sandbox/` | the end-to-end fixtures, comparison script and runbook |
| `docs/` | model card and README generators, this diagram |
