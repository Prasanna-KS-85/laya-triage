# Deployment as a GitHub Action

## The composite Action and the Linux lock

The Action is defined in `action.yml`; the next section describes its steps and caches. At the end of every run it uploads the JSON log as an artifact (FR-7). Inputs reach the scripts only through environment variables, never through expressions inside a shell script (NFR-6).

The dependencies are pinned by `constraints-linux.txt`, a lock of {{n_pins}} packages generated by the `lock-linux` job of CI: `pip freeze --all` on a hosted runner, CI run {{fact:lock_run}} ({{fact:lock_os}}). Torch is installed from the CPU-only wheel index, with one retry through an extra index if the CPU index alone fails, so the runner never downloads the much larger CUDA build. Appendix A lists every pin.

## Caching, the issues-event finding and warm-cache

{{include:DEEP_DIVE#deployment-and-caches}}

The cache sizes recorded on the sandbox: {{fact:cache_sizes}}. Phase 0 had measured the files that `laya.load` needs at {{fact:minimal_download}}, against {{fact:full_snapshot}} for the whole model repository, so only part of the snapshot is downloaded and cached. The finding that runs triggered by an `issues` event cannot save caches was not foreseen in the design; it appeared in the first cold sandbox run, whose two cache saves were refused with "{{fact:cache_denied}}" while the run itself succeeded. Without a remedy, a repository whose workflow runs only on issues would stay cold once GitHub evicted its caches. The remedy is the `warm-cache` input: a run with it validates the configuration, loads the model and classifies one built-in synthetic issue, so that the normal save steps run, but it reads no issues and makes no GitHub API call.

The warm-cache mode was verified by manual dispatch: run {{run_warm_cache}}, started from deleted caches, saved both caches, and the next issue-triggered run ({{run_warm_issue}}) restored both. A schedule is configured in the example workflow (cron `{{cron}}`, twice a week, with margin against the eviction of caches unused for a week). The committed records contain no run started by that schedule; `results/phase4.md` records it as "{{fact:schedule_not_observed}}".

## Sandbox validation

The Action was validated end to end on a private sandbox repository, following the runbook in `sandbox/README.md`. The test material is {{n_fixtures}} fixtures written for this project (`sandbox/issues.json`, Appendix D), never issue text from the benchmark. They cover every class, template mismatches, ambiguous, empty, title-only, long-log, markdown, non-English, prompt-injection-like and emoji cases, and {{n_skip_fixtures}} skip cases. Before the sandbox runs, `sandbox/make_expected.py` ran the production path locally and wrote the expected label, probabilities and decision of every fixture to `sandbox/expected_local.json`.

`sandbox/compare.py` compared the JSON logs of the runner with the local expectations (same label, a probability difference of at most {{fact:compare_tolerance}}, same decision):

- **Runner parity, dry-run.** The {{n_fixtures}} issue runs gave {{fact:compare_dry_run}}. After the dry-run no issue carried a label beyond those set at creation, and no comment had been posted (FR-4).
- **Apply mode.** A backfill in apply mode gave {{fact:compare_apply}}: `type: bug` was added where the bug confidence reached its threshold and the escalation label everywhere else. Two issues opened by hand in the web UI with comments enabled showed one applied label and one escalation with comment template (b).
- **Backfill and idempotency.** A second backfill over the same issues gave {{fact:compare_idempotent}}.
- **Pull-request exclusion.** {{fact:pr_excluded}}.
- **Labels at creation.** The fixtures created with a type label or the escalation label were skipped with the matching reason, which confirmed that labels added at creation are present in the `issues.opened` event.

Three observations from the fixtures are limitations rather than failures and are repeated in chapter twelve: the German fixture S17 was auto-labelled `bug` (there is no language guard), the prompt-injection-like fixture S18 moved the prediction to `feature` (issue text can steer the label, within the {{n_labels}} options), and fixtures with an absent and an empty body give identical results.
