## Splits and dropped rows

- `test` = all 1,500 official test rows, untouched; evaluated once.
- Official-train rows whose content (`title + "\n" + body`) also occurs in official test, or more
  than once in official train, are dropped (all copies). See the generated table below.
- `val` = 20% (round half up) of each repo × label cell of the kept rows, seed 42, never from the
  Phase 0 wording sample (`results/phase0_sample_ids.txt`, forced into `train`).
- `train` = the remaining kept rows.
- Manifests: `data/manifests/{train,val,test}.txt` (`<id>\t<content_sha1>`, raw-CSV order) and
  `data/manifests/dropped_train.txt` (`<id>\t<content_sha1>\t<reason>`).
- Processed rows: `data/processed/train.jsonl` (§8.5) and `{val,test}.jsonl` (§8.6, with an
  `"id"` field, which `laya-evals validate` accepts). Row order equals manifest order.

## Limitations

- **Balanced, not natural.** Exactly 100 issues per repo × label in each file. Real repositories
  have very different class mixes, so calibration and thresholds fitted here may not transfer
  (PROJECT_SPEC.md R11).
- **Random, not temporal, split.** Upstream train and test are not separated by time, and our val
  split is random within cells, so the numbers do not measure drift to future issues.
- **Empty bodies.** 2 official test bodies are empty in the raw data; 4 more bodies (vscode feature
  requests made only of template HTML comments) become empty after cleaning. These are classified
  on the title alone.
- **Label noise.** Labels come from upstream repository labels; some issues are plausibly mislabelled
  (for example identical content labelled `bug` in train and `feature` in test). See the manual
  review below.
- **No IDs.** The data has no issue numbers or URLs, so issues cannot be traced back to GitHub, and
  deduplication against other datasets must use content hashes.
- **Unfenced logs.** Preprocessing collapses fenced code blocks only; long logs pasted without a
  fence are cut only by the 6,000-character cap.

## Manual review (30 rows)

Sample: 30 train rows drawn uniformly at random (seed 42; data/processed/review_sample_30.md, gitignored): 14 bug / 5 feature / 11 question; react 9, tensorflow 9, vscode 5, bitcoin 4, opencv 3.
Method: each row judged against the frozen question definitions using its title and the first 600 characters of the cleaned body; text beyond 600 characters was not reviewed. Reviewer: owner, with an AI first pass (Claude) on the same view.
Labels: 24 ok / 4 doubtful / 2 wrong.
- wrong: train-0237 (gold question), train-0408 (gold feature).
- doubtful: train-0285 (question), train-0705 (feature), train-0875 (question), train-1082 (question).
- by gold class: bug 14/14 ok; feature 3 ok, 1 doubtful, 1 wrong (of 5); question 7 ok, 3 doubtful, 1 wrong (of 11).
Cleaning: 30 ok / 0 harmed. No row lost the content that identifies its type. Bodies cut at 6,000 characters: train-1075, train-1155, train-1401 (the description is at the start in all three).
Patterns:
- Template type vs gold label: in 5 of the 11 question rows (train-0237, 0260, 0285, 0864, 0875) the author's own template choice (bug or feature) differs from the gold label. The cleaned text keeps those template lines, which help on bug/feature rows and mislead on these. Expect question to be the hardest class; this matches the Phase 0 zero-shot error pattern (gold question predicted as bug) and risk R2.
- Template boilerplate not removed by §8.4 (by design): empty-field placeholders and section headings in 7 of 9 tensorflow rows and 5 of 9 react rows; system-info blocks in vscode rows (train-0864, 0875). It uses tokens before the author's text, mostly a concern at 512 tokens.
- Label noise estimate: about 7% clearly wrong and 20% wrong-or-doubtful (n=30, wide uncertainty).
